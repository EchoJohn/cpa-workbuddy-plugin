# new-api 瞬时 503 批量拒绝（CPA 侧无感知）根因诊断

- 编号：BUG-NEWAPI-PERF-MONITOR-503-20261012
- 发现时间：2026-10-12 00:15（北京时间，用户报告"new-api 突然有一些请求超时，但 CPA 并没有发现问题"）
- 判定时间：2026-10-12 01:00（北京时间）
- 状态：已定位根因（new-api 侧 `SystemPerformanceCheck` 中间件按 CPU 阈值快速拒绝），生产阈值与宿主负载证据齐全；**本仓库（cpa-plugin）无代码改动**，修复方向属 new-api 项目，按跨项目只读红线仅产出改动计划
- 关联：`doc/4-bugs/2026-10-11_212700_deepseek多服务商同名认领导致推理零首字节断开根因诊断.md`（同链路不同根因）、`doc/4-bugs/2026-10-11_233200_Token用量记录在宿主配置热重载窗口被永久丢弃根因诊断.md`

## 1. 现象

调用链：客户端 → `https://api.luode.vip/v1`（nginx 容器，`proxy_read_timeout 600s`）→ new-api（容器 `new-api`，`PORT=5566`，channel 4 `BaseURL: http://127.0.0.1:8317`）→ CPA 容器 `cli-proxy-api`（host network `:8317`）→ provider 插件。

用户可见症状：**部分请求"超时/突然断开"，但 CPA 侧日志完全正常（全 200），两侧现象不一致**。

实测两侧数据（同一窗口）：

| 侧 | 观测 |
| --- | --- |
| new-api | 近 30 分钟 **194 次 503**；近 12 小时 **2470 次 503**（其中用户 IP `183.239.175.194` 123 次，其余来自外部扫描 IP `107.173.42.94`） |
| CPA `cli-proxy-api` | 同期 `/v1/responses` 全 200，零 5xx（6h 内仅 4 次 502 属插件安装接口，与推理无关） |
| nginx | 用户 IP 的 `/v1/responses` 有 503/502 透传记录（UTC 15:15–16:18 集中，即北京 23:15–00:18） |

## 2. 决定性判据（区分 503 来源）

new-api 里能产生 503 的路径只有两处，二者行为截然不同：

| 来源 | 代码位置 | 是否写 `logs` 表(type=5) | 是否写 `[ERR]` 日志 | 耗时特征 |
| --- | --- | --- | --- | --- |
| `SystemPerformanceCheck` | `middleware/performance.go:14-38` | **否** | **否** | 微秒级（阈值判断即 abort） |
| `Distribute` 无可用渠道 | `middleware/distributor.go:179/183/194` → `abortWithOpenAiMessage` | 是（`logger.LogError` → `logs` 表） | 是 | 毫秒级起（含 DB/选渠道开销） |

实测 503 样本：

```
[GIN] 2026/10/12 - 00:32:13 | relay | 202610111632130751594548268d9d6rsDEoKIt | 503 |     428.705µs | 183.239.175.194 |    POST /v1/responses
[GIN] 2026/10/12 - 00:32:12 | relay | 202610111632123576343628268d9d63MPcAdHG | 503 |      24.735µs |   107.173.42.94 |    POST /v1/chat/completions
```

关键事实：

1. 全部 503 耗时 **20µs ~ 0.6ms**，无一进入毫秒级选渠道流程。
2. 逐行检查 503 上下文（`/app/logs/oneapi-20261011135200.log` 行 653965-653972、23777-23806），**503 行前后无任何 `[ERR]` 伴生行**，而 `abortWithOpenAiMessage` 必写 `[ERR]`。
3. `logs` 表近 1 小时只有 `type=2`（3119 条）与 `type=3`（2 条），**无 `type=5`（错误日志）**——与"503 从未走 abortWithOpenAiMessage"完全一致。

### 2.1 三重交叉验证（2026-10-12 01:00 补齐）

**验证一：503 与 `[ERR]` 的伴生率对比**

对完整日志文件做"503 行的前一行是否为 `[ERR]`"的全量统计：

| 状态码 | 总数 | 前一行是 `[ERR]` 的 | 伴生率 |
| --- | --- | --- | --- |
| 503 | 2470 | 9 | **0.36%** |
| 500 | 201832 | 136023 | 67.4% |

500 大量伴生 `[ERR]`（走 `abortWithOpenAiMessage`/`logger.LogError`），而 503 几乎完全不伴生——证明 503 走的是**另一条不写错误日志的路径**。

**验证二：那 9 条伴生 `[ERR]` 的 503 全部是毫秒/秒级**

逐条核对（`/app/logs/oneapi-20261011135200.log`）：

```
[ERR] 14:43:47 | user 1 | No available channel for model qwen-3.8-max under group 正常分组 (distributor)
[GIN] 14:43:47 | 503 |     5.068602ms   ← distributor 类
[ERR] 15:29:57 | relay error: auth_not_found: no auth available (providers=workbuddy-ai-provider, model=deepseek-v4.1-flash)
[GIN] 15:29:57 | 503 |  1.916401882s     ← 上游无 auth
[ERR] 15:35:22 | user 1 | No available channel for model qwen-3.8-flash under group 正常分组 (distributor)
[GIN] 15:35:22 | 503 |   17.081293ms    ← distributor 类
[ERR] 15:36:21 | relay error: auth_not_found: no auth available (providers=workbuddy-ai-provider, model=deepseek-v4.1-flash)
[GIN] 15:36:21 | 503 |   2.04363628s     ← 上游无 auth
```

即：**带 `[ERR]` 的 503 全部是毫秒/秒级**（5ms、17ms、1.9s、2.0s），**其余 2461 条 503 是微秒级且无 `[ERR]`**。两类 503 在耗时上完全分离，无重叠。

**验证三：响应体字节数分叉（nginx 侧实证）**

按 nginx 记录的响应体长度分桶：

| 来源 IP | 143 字节 | 193 字节 | 208 字节 | 210 字节 | 合计 |
| --- | --- | --- | --- | --- | --- |
| 用户 IP `183.239.175.194` | **77** | 3 | 1 | 2 | 83 |
| 扫描 IP `107.173.42.94` | 2346 | 0 | 0 | 0 | 2346 |

对照 `performance.go` 的报文构造（`c.JSON(err.StatusCode, gin.H{"error": err.ToOpenAIError()})`，`ToOpenAIError` 走 `default` 分支填 `type=e.errorType`=`new_api_error`）：

```
{"error":{"message":"system cpu overloaded (current: 93.2%, threshold: 90%)","type":"new_api_error","param":"","code":"system_cpu_overloaded"}}
```

实测长度 **恰好 143 字节**（`current: 100.0%` 时 144 字节，其余百分比形态均为 143）；memory/disk 变体分别为 149/145 字节。

而 distributor 类走 `abortWithOpenAiMessage` → `MessageWithRequestId`（`common/utils.go:293` 追加 ` (request id: <32位>)`），报文长 **190+ 字节**（实测样例 198 字节），与观测到的 193/208/210 字节吻合。

⇒ **143 字节 = performance 类**，**193/208/210 字节 = distributor 类**，两类在长度上完全分离。

**综合结论**：用户 IP 在 12 小时内的 83 条 503 中，**77 条（92.8%）是 `SystemPerformanceCheck` 的 CPU 阈值拒绝**，6 条（7.2%）是上游账号池问题（无可用渠道 / 无 auth）。

⇒ 503 **只能来自 `SystemPerformanceCheck`**（微秒级那批）。

### 2.2 关闭开关后的实测验证（2026-10-12 01:05，决定性）

用户在管理台关闭「系统性能监控」后（`options` 表实测 `performance_setting.monitor_enabled = false`，写于 `2026-10-12 00:43:10` 的 `PUT /api/option/`），按同一口径复测：

| 窗口 | 143 字节 503（performance 类） | 全部 503 | `client_gone` | CPA `upstream execution failed` |
| --- | --- | --- | --- | --- |
| 关闭前（11/Oct 15:00–16:43 UTC） | **382** | — | — | — |
| 关闭后（最近 25 分钟） | **0** | **0** | 0 | 0 |

关闭后四类失败面**同时归零**（`new-api` 503=0、`client_gone`=0、CPA `upstream execution failed`=0、nginx 用户 IP 非 2xx=0）。

即 **143 字节的 503 完全归零**，且连外部扫描 IP `107.173.42.94` 打 `/v1/chat/completions` 的 503 也一并消失（该 IP 此前 2346 条 503 全部为 143 字节）——因为扫描 IP 打的是 `/v1/chat/completions`，同样落在 `relayV1Router` 上、同样被 `SystemPerformanceCheck` 拦截。

**用户报告时刻（北京 00:10–00:35）的精确对齐**：`new-api` 日志在该时段记录到 19 条用户 IP 的 503，成批分布在 5 个时间簇（00:18:08–00:18:10、00:18:45–00:18:49、00:19:17–00:19:19、00:20:05–00:20:08、00:23:48–00:23:50、00:32:07–00:32:13），正是用户描述的"突然断开"形态——**同一秒内多个请求一起被拒、几秒后恢复**，与"5 秒采样窗口内 CPU 越线则整窗全拒"的机制完全吻合。

**这构成"关闭开关 → 503 消失"的因果闭环实证**，不再依赖推理。

> 注：`new-api` 容器 `StartedAt=2026-10-11T05:51:59Z`，配置变更后**未重启**，说明 `performance_setting` 走的是热生效路径（`model/option.go:658` 在配置写入时调用 `performance_setting.UpdateAndSync()` → `common.SetPerformanceMonitorConfig`），无需重启容器。

## 2.3 结论对"关掉就 OK 了吗"的回答

**对于「new-api 突然返回 503、CPA 无感知」这一现象：是的，关闭后已实测归零。**

但必须区分清楚两件事，避免把另一个独立问题误判为已解决：

| 现象 | 是否由性能监控引起 | 关闭后是否解决 |
| --- | --- | --- |
| new-api 微秒级 503（143 字节、无 `[ERR]`、CPA 零记录） | **是** | **已解决（实测归零）** |
| new-api `client_gone`（真·超时断开，`frt=-1000`、`completion_tokens=0`） | 否 | 未解决（另有根因，见 `2026-10-11_212700_*.md`） |
| CPA `upstream execution failed`（qoder-ai 60s `INTERNAL_ERROR`） | 否 | 未解决（上游行为，需另立 Bug） |
| 上游无可用渠道 / 无 auth 的 503（193-210 字节、带 `[ERR]`） | 否 | 未解决（账号池问题） |

关闭性能监控**只消除第一类**（本次会话复现的那类）。若用户感知的"超时/断开"实际来自后三类，则关闭开关不会改善。

**残余风险（关闭监控不等于问题消失）**：宿主 CPU 长期在 70–93% 徘徊、`dockerd` 持续占用 1.3–1.5 核这一**底层负载问题依然存在**，只是不再有中间件把它转成 503。请求会继续被处理，但：① 高 CPU 会拉长首字节延迟（实测 `frt` 3.5–10.9s）；② 极端负载下可能出现新的超时形态；③ 扫描 IP 的海量请求（6h 内 10 万+）仍在消耗 CPU。根治仍需处理 dockerd 高 CPU 与日志膨胀（见第 6 节第 3 项）。

## 3. 根因

`middleware/performance.go` 的 `SystemPerformanceCheck` 挂在 relay 路由组上（`router/relay-router.go:71` `relayV1Router.Use(middleware.SystemPerformanceCheck())`，另有 `/pg`、`/mj`、`/v1beta`、video、task-plugin 等组），在每个 relay 请求进入鉴权/分发**之前**读一次缓存的系统状态，超阈值即直接 503 并 `Abort`：

```go
// middleware/performance.go:41-71
config := common.GetPerformanceMonitorConfig()
if !config.Enabled { return nil }
status := common.GetSystemStatus()
if config.CPUThreshold > 0 && int(status.CPUUsage) > config.CPUThreshold {
    return types.NewErrorWithStatusCode(..., "system_cpu_overloaded", http.StatusServiceUnavailable)
}
if config.MemoryThreshold > 0 && int(status.MemoryUsage) > config.MemoryThreshold { ... }
if config.DiskThreshold > 0 && int(status.DiskUsage) > config.DiskThreshold { ... }
```

配置与采样口径：

- 阈值默认 `CPU=90 / Mem=90 / Disk=95`（`setting/performance_setting/config.go:36-39`）；生产 `options` 表**无 `performance_setting.*` 覆盖项**，即跑默认值。
- 采样器 `common/system_monitor.go:37-50` 每 **5 秒**刷新一次，写进 `atomic.Value`；`GetSystemStatus` 读的是**最近一次 5 秒采样的瞬时值**（非滑动平均）。
- CPU 取 `cpu.Percent(0, false)` = **宿主全机 4 核整体使用率**；内存取 `mem.VirtualMemory().UsedPercent` = **宿主全机**（容器内 `/proc/meminfo` 即宿主视图）；磁盘取缓存目录所在分区。

宿主实测负载（本次会话连续采样）：

| 指标 | 实测 | 阈值 | 判定 |
| --- | --- | --- | --- |
| CPU（全机 4 核） | 长期 70–93%，多次采样达 **90% / 92% / 93%** | 90 | **反复越线** |
| 内存 UsedPercent | 65–71% | 90 | 未越线 |
| 磁盘 | 70%（21G/29G） | 95 | 未越线 |

⇒ 触发条件 = **CPU 瞬时越过 90%**，与"成批出现几秒后自动恢复"的形态完全吻合（一个 5 秒采样窗口内全拒，下个窗口回落即恢复）。

**CPU 尖峰的来源**：宿主 `dockerd` 进程长期占用约 **1.3–1.5 核**（`top` 采样 200% CPU，`/proc/<pid>/stat` 增量折算 13000–15600‰ 即 1.3–1.5 核），累计 CPU 时间 utime+stime ≈ 7163 秒/28 天。而其下所有容器合计仅约 25% CPU（cli-proxy-api ~15%、mysql ~3.5%、nginx ~2.5%）。即 **CPU 尖峰主要来自 docker 守护进程本身，而非业务容器**。旁证：`dockerd` 的 `syscr`（读系统调用数）达 **1437 亿次**，`new-api` 容器日志已达 **121MB** 且 `json-file` 驱动未对既有容器应用 `max-size/max-file`（`docker inspect` 显示 `Opts=map[]`），容器内 `/app/logs` 另有 **961MB / 46 文件**（含 318MB、225MB、205MB 单个文件）——持续的日志 I/O 是 dockerd 高 CPU 的合理主因。

## 4. 为什么 CPA 完全"看不到问题"

`SystemPerformanceCheck` 位于 **relay 路由最前置**（`relay-router.go:71` 在 `TokenAuth`、`ModelRequestRateLimit`、`Distribute` 之前），请求在**尚未转发给 CPA** 时就被 503 拒绝。因此：

- CPA 容器不会收到这批请求，日志自然全 200、零异常；
- new-api 的 `logs` 表也不会记录（该路径不走 `abortWithOpenAiMessage`）；
- 结果就是"new-api 侧有异常、CPA 侧无感知"的观测割裂。

对照记忆 [[reference-inference-chain-observability]] 的既有判据："判断推理是否真的断开看 new-api 不看 CPA"——本次进一步明确：**new-api 的 503 还分'前置性能拒绝'与'分发无渠道'两类，前者 CPA 必然无感知，只有后者才会在 CPA 留痕**。

## 5. 复现与证据

- 复现路径：在宿主 CPU 越线窗口内调用 `POST http://127.0.0.1:5566/v1/responses`（带有效 token）。
- 稳定性：**间歇性、成批出现**。本次主动探测（累计 900+ 次请求：240 次串行 + 480 次并发 3 路 + 480 次并发 12 路）**全部返回 200**，未在探测窗口命中——因 503 依赖"采样瞬间 CPU > 90%"这一外部条件，主动压测反而难以命中；对照窗口内 `docker logs --since 30m new-api | grep -c '| 503 |'` = 194 条，证明真实用户流量下确实在持续发生。
- 证据清单：
  1. 503 耗时分布：20µs–0.6ms（`docker logs new-api` 的 GIN 行）。
  2. 503 无 `[ERR]` 伴生、`logs` 表无 `type=5`（近 1h）。
  3. 宿主 CPU 采样多次 ≥ 90%（`/proc/stat` 增量法，0.5s 间隔，峰值 93%）。
  4. `dockerd` 单进程占 1.3–1.5 核，容器合计约 25%。
  5. 生产阈值确认为默认 90（`options` 表无覆盖项）。
  6. 代码路径：`middleware/performance.go:14-71`、`common/system_monitor.go:37-50`、`router/relay-router.go:71`。

## 6. 处置与修复

### 6.1 已执行（用户操作，2026-10-12 00:43:10）

用户在 new-api 管理台「运维 → 性能 → 系统性能监控」关闭「启用性能监控」开关，对应 `options` 表 `performance_setting.monitor_enabled = false`。

- 生效方式：**热生效，未重启容器**。写入链路为 `PUT /api/option/` → `controller/option.go:128 UpdateOption` → `model/option.go:658` 命中 `performance_setting` 分支调用 `performance_setting.UpdateAndSync()` → `common.SetPerformanceMonitorConfig({Enabled:false})`，之后 `SystemPerformanceCheck` 在 `config.Enabled==false` 时直接 `return nil`（`middleware/performance.go:43-45`）。
- 实测效果：关闭前 382 条 143 字节 503 → 关闭后 **0 条**（见 2.2 节）。
- 回滚：管理台重新打开开关，或将 `performance_setting.monitor_enabled` 置回 `true`；默认阈值为 CPU 90 / 内存 90 / 磁盘 95（`setting/performance_setting/config.go:36-39`）。

### 6.2 仍建议的后续治理（属 new-api 项目，跨项目只读，仅产出计划）

本仓库为 `cpa-plugin`，与 `F:\new-api` 是并列兄弟项目。按项目级"跨项目写入红线"，**本会话不得修改 new-api 任何文件**，以下仅为改动计划，需在 new-api 项目目录下新开会话执行。

关闭监控只是"拆掉了把高 CPU 转成 503 的那道闸"，底层负载未动。按优先级：

1. **（治本）把单点瞬时采样改成带滞回的判定**：`common/system_monitor.go:37-50` 目前 5 秒一采、取瞬时值直接比较，导致"擦线即全拒"。建议改为连续 N 次采样超阈值才拒绝，或引入滞回（>90% 进入、<80% 退出）。这样可重新启用监控而不误伤。
2. **（除源）降低 dockerd 的 CPU 占用**：为既有容器补 `log-opts`（`daemon.json` 已有 `max-size=50m,max-file=3` 但未应用到存量容器，`docker inspect` 显示 `Opts=map[]`，需重建容器生效）、清理 new-api 容器内 961MB 历史日志（`/app/logs`，含 318MB、225MB、205MB 三个大文件）。这是 CPU 尖峰的实际来源。
3. **（加固）限制外部扫描流量**：`107.173.42.94` 单 IP 6h 内产生 10 万+ 请求，既是日志膨胀与 CPU 占用的放大器，也是 503 计数的主要污染源。可在 nginx 层按 IP 限流或封禁。

## 7. 未覆盖与后续风险

- **关闭监控不解决另外三类失败**（本次已明确区分，勿混淆）：
  1. new-api `client_gone`（真·超时断开）：关闭后最近 25 分钟计数为 0，但历史上 12h 内共 14 次，根因是"会话被钉在挂起账号 + 60s 零字节静默"，见 `2026-10-11_212700_*.md`。
  2. CPA `upstream execution failed`（qoder-ai `Qwen3.8-Flash/Max` 稳定 60s `INTERNAL_ERROR`）：关闭后仍在发生（最近 1h 内 7 次），属上游行为。
  3. 上游账号池类 503（`No available channel` / `auth_not_found`，193-210 字节带 `[ERR]`）：属账号运营问题。
- **未确证 dockerd 高 CPU 的精确成因**：`syscr` 1437 亿次与日志体积指向日志 I/O，但未做 `perf`/`strace` 级归因；也未排除 live-restore、健康检查、镜像层等其他因素。
- **主动压测无法稳定复现**：本次 900+ 次探测零命中，说明该 503 高度依赖外部 CPU 条件。后续验证应以"真实流量下按响应体字节数（143 vs 190+）分桶统计 503"为判据，而非压测。
- **监控关闭后的可观测性缺口**：关闭后若宿主机真的过载（如内存耗尽、磁盘写满），将不再有任何前置保护，请求会以更难诊断的形态（超时、OOM）失败。建议按 6.2 第 1 项改造后重新启用。

## 8. 结论

"new-api 突然有一些请求超时、但 CPA 没发现问题"不是链路断开，而是 **new-api 自身的 `SystemPerformanceCheck` 性能监控中间件在宿主 CPU 瞬时越过 90% 阈值时，于 relay 路由最前置直接返回 503 并 abort**；因为该路径不写 `logs` 表、不写 `[ERR]` 日志、也不转发给 CPA，所以呈现出"new-api 有异常、CPA 全正常"的割裂观测。CPU 尖峰主要来自宿主 `dockerd` 进程（长期占用 1.3–1.5 核，疑似容器日志 I/O 放大），而非业务容器。

**对"关掉性能监控就 OK 了吗"的直接回答：对本次复现的这一类（微秒级 143 字节 503）——是的，已实测归零（382 → 0），且热生效无需重启。** 但它只消除这一类；`client_gone` 真超时、qoder-ai 上游 60s 失败、账号池类 503 这三类独立问题不受影响，若用户感知的"断开"来自后三类，关闭开关不会改善。底层 dockerd 高 CPU 负载也未解决，建议按第 6.2 节继续治理。
