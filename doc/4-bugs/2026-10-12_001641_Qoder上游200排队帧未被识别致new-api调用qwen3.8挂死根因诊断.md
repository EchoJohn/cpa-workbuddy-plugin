- 判定时间：2026-10-12 00:16（北京时间）
- 状态：**已修复、已发布并完成生产热重载验收**（qoder-ai-provider **0.1.9** / qoderwork-provider **0.9.30**；CI run `38157167623` / `38157165743` 均 success；registry 已同步、远端 14/14 平台 ALL PASS；生产 `plugin hot reloaded active_version=0.1.9 / 0.9.30`、零容器重启、落盘 `.so` sha256 与本地 zip 一致；修复后 112KB prompt 由 60.57s 挂死变为 3.90s 正常返回，两报障模型经渠道 key 直测均 200）。发布验收证据见 `doc/5-tests/2026-10-11_164802_Qoder排队帧识别回归.md` 第 7 节
- 关联历史：`doc/4-bugs/2026-10-11_212700_deepseek多服务商同名认领导致推理零首字节断开根因诊断.md` 第 6 节「未修复项」已预告本 Bug（"qoder-ai-provider 的 Qwen3.8-Flash/Max 存在同形态问题……需另立 Bug 单"）

## 1. 现象

用户报告：从 new-api 请求 CPA 的 `qwen-3.8-flash`、`qwen-3.8` 两个模型不可用，但 **CPA 面板自身的「测试」按钮却显示成功**。

- new-api 渠道测试（`GET /api/channel/test/5?model=qwen-3.8-flash`）多次记录 `use_time_seconds` 高达 124 / 165 / 386 秒，最终 `stream_status: {"end_error":"context canceled","end_reason":"client_gone","status":"error"}`、`frt: -1000`（首字节从未产生）、`completion_tokens: 0`。
- new-api 消费日志明确写入 `"content":"上游没有返回计费信息，无法扣费（可能是上游超时）"`。
- 同时段 CPA 面板手动测试：`[qoder-ai] manual active ping test success ... with model Qwen3.8-Flash (took 219ms / 366ms / 1.102s)`——**面板快速报成功**。

即：**面板测试通过 ≠ 真实推理可用**（与 2026-10-10 content 数组 503 那次同一类"两条路径不同"陷阱）。

## 2. 复现路径与环境

- 环境：生产 CPA（`45.207.222.65:18998`，容器 `cli-proxy-api`，host network `:8317`），qoder-ai-provider **0.1.8**（落盘 `.so` sha256 `4ae2fea7f6cc04d19c7a08e4f20c4870f8fe58c319eecd760c61d3410fa819e7`）。
- 链路：客户端 → nginx `api.luode.vip` → new-api（channel 4/5，`BaseURL: http://127.0.0.1:8317`）→ CPA → qoder-ai-provider → 阿里 Qoder 上游。
- new-api 侧渠道模型串：channel 4 = `...,gemini-3.8-flash,qwen-3.8-flash`；channel 5 = `custom,qwen-3.8-flash,qwen-3.8`。
- 直测命令（绕开 new-api，直打 CPA，使用 new-api channel 5 的 key）：
  ```bash
  curl -s -N -D /tmp/h.txt -o /tmp/body.txt \
    -H "Authorization: Bearer <channel-key>" -H "Content-Type: application/json" \
    -d '{"model":"qwen-3.8-flash","messages":[{"role":"user","content":"<长 prompt>"}],"stream":true,"max_tokens":8}' \
    http://127.0.0.1:8317/v1/chat/completions
  ```

### 2.1 决定性实测：同一模型名，仅 prompt 长度不同，行为完全相反

| 请求 | prompt 大小 | HTTP | 首字节 | 总耗时 | 结果 |
| --- | --- | --- | --- | --- | --- |
| `qwen-3.8-flash`，`hi` | 112 B | 200 | 0.84s | 1.47s | **正常**返回正文 |
| `qwen-3.8-flash`，pad=500 词 | 22.6 KB | 200 | 1.28s | 2.10s | **正常**返回正文 |
| `qwen-3.8-flash`，pad=1500 词 | 67 KB | 200 | 0.34s | 3.49s | **正常**返回正文（含 reasoning_content） |
| `qwen-3.8-flash`，pad=2500 词 | 112 KB | 200 | 0.0005s | **60.5s** | **挂死**，返回排队错误帧后死等 |
| `qwen-3.8`，pad=2500 词 | 112 KB | 200 | 0.0004s | **60.3s** | **挂死**，同上 |
| `qwen-3.8-flash`，pad=2500 词，连测 3 次 | 112 KB | 200 | ~0.0004s | 60.6 / 60.7 / 61.0s | **3/3 稳定复现** |
| `Qwen3.8-Flash`（点号大写） | 短 | 200 | — | 1.10s | 正常 |
| `qfmodel`（上游内部键） | 短 | 200 | — | 1.36s | 正常 |
| `qwen3.8-flash`（点号） | 短 | 400 | — | — | `unknown provider for model`（CPA 目录无此名） |

**结论**：与模型名写法无关（`qwen-3.8-flash` 与 `qwen-3.8` 均可路由到 qoder-ai-provider），触发条件是**请求体足够大（约 >70KB / 输入 token 数高）**时上游把请求投入排队，返回 HTTP 200 + 业务排队帧。

### 2.2 挂死响应的完整报文（112KB prompt 实测）

响应头：`HTTP/1.1 200 OK`、`Content-Type: text/event-stream`。

响应体（477 字节，关键部分）：
```
data: {"code":"403","message":"{\"code\":\"10605\",\"message\":\"{\\\"isQueued\\\":true,\\\"modelKey\\\":\\\"qfmodel\\\",\\\"queueCount\\\":0,\\\"queueType\\\":\\\"p3\\\",\\\"retryAfterSeconds\\\":30,\\\"serviceAvailable\\\":false,\\\"waitTime\\\":30}\"}"}

: keep-alive
: keep-alive
: keep-alive

data: {"error":{"message":"upstream stream read error: stream error: stream ID 1007; INTERNAL_ERROR; received from peer","type":"server_error","code":"internal_server_error"}}
```

即：上游在 HTTP 200 下先吐一个**顶层 `code:"403"`** 的排队帧（内嵌 `10605 / isQueued:true / serviceAvailable:false / retryAfterSeconds:30`），随后保持 HTTP/2 长连接**只发 `: keep-alive` 心跳**，直到约 60 秒后由对端复位流（`INTERNAL_ERROR`）。

## 3. 根因

**单点根因**：`qoder-ai/stream.go` 的 SSE 解析器 `parseQoderSSEChunk` **不识别顶层 `code` 字段的排队/错误帧**，把该帧当成"无关行"直接丢弃；插件因此读不到任何终止信号与错误信息，`scanner.Scan()` 死等上游 Keep-Alive 连接约 60 秒，最终由对端 HTTP/2 复位才退出——客户端在整个窗口内零字节。

三层证据：

1. **解析器丢弃（代码级复现）**。`parseQoderSSEChunk`（`qoder-ai/stream.go:92-141`）只认四种形态：`[DONE]`、嵌套 `outer["body"]`、扁平 `outer["choices"]`、`outer["id"]`、以及 `outer["error"]`；顶层 `code` 帧不属于任何一类，落到末尾 `return "", false` → 在 `pumpUpstreamStream`（`:207-333`）与 `collectUpstreamStreamQoder`（`:367+`）的扫描循环里被 `continue` 跳过。本地用 `go run` 逐字复刻该函数验证：
   ```
   line0: parsed="" done=false errFrame=""     ← 排队帧被完全丢弃
   line1: parsed="{...choices...}" done=false errFrame=""
   line2: parsed="" done=true  errFrame=""
   ```
   同时 `sseErrorFrame`（`:756-779`）只从 `obj["error"]` 取消息，对顶层 `code` 帧恒返回 `""`——**双层都不认**。

2. **上游行为（生产实测）**：大请求被投排队（`isQueued:true`、`serviceAvailable:false`、`retryAfterSeconds:30`），HTTP 200 长连接不主动关闭，`: keep-alive` 心跳持续约 60s，随后对端复位。这解释了 CPA 日志里规律性的 `duration=59.8s ~ 1m0.2s` + `err=upstream stream read error: stream error: stream ID N; INTERNAL_ERROR; received from peer`（近 3 小时 20+ 条，全部集中在 `Qwen3.8-Flash` / `Qwen3.8-Max`）。

3. **面板测试为何"成功"（假成功盲区）**：`sendActivePingQoder`（`qoder-ai/active_ping.go:132-171`）用 `"hi"` 极小 prompt，不会触发排队；且它"读到首个数据块即视为流已建立"（`buf := make([]byte, 512); reader.Read(buf); return nil`）——即使读到排队帧也会盲判成功。**两条路径的差异（prompt 规模 + 是否校验帧内容）导致"测试通过、推理挂死"。**

### 3.1 与既有记录的关系（非重复缺陷）

- 与 `2026-10-10 content 数组 503` **不同**：那次是请求侧 payload 解析失败（插件返回 503），本次是响应侧错误帧识别缺失（插件不返回错误，而是挂死）。
- 与 `2026-10-11 deepseek 同名认领` **不同**：那次是会话亲和 + Trae 账号挂起；本次触发者是 **qoder-ai-provider**，根因是排队帧不可识别。该文档第 6 节已把本现象列为"未修复项"，本轮完成根因收敛。

## 5. 修复建议（待用户确认后实施）

按根因修复、最小改动、不打补丁的原则，**核心修复点唯一**：让解析器识别顶层 `code` 错误帧，使插件立即以错误收尾而非死等。

1. **`parseQoderSSEChunk` 增加第 4 类形态**：识别顶层 `code` 且为错误语义（`code` 存在且非 `"0"`/`"200"`，或含 `isQueued` / `serviceAvailable:false`）的帧，返回该 payload 供上层判定。
2. **`sseErrorFrame` 扩展**：除 `obj["error"]` 外，识别顶层 `code` + `message` 组合（`message` 可能是内嵌 JSON 字符串，需二次解析提取 `10605` / `isQueued` 语义），产出可读错误文本。
3. **两条执行路径统一生效**：`pumpUpstreamStream`（异步）与 `collectUpstreamStreamQoder`（同步）都要走该判定；命中时立即 `stream.Close()` + `break`，并按既有 `shouldRotateOnUpstreamErr` / `noteAccountFailure` 逻辑处理（零泄漏时可换号，已泄漏则透传错误）。
4. **探活与面板测试对齐**（`sendActivePingQoder`）：把"读到首字节即成功"改为"读到首个**有效业务帧**才成功，首帧为错误/排队帧即返回失败"——消除 §3 第 3 点的假成功盲区（该改法已在项目 skill `project-cpa-workbuddy-plugin-sse-and-ping-optimization-rules` 规则二.2 中作为强制契约记录，但 qoder-ai 的 `sendActivePingQoder` 尚未落实内容校验）。
5. **横向同步**：`qoderwork` 与 `qoder-ai` 的 `stream.go` / `active_ping.go` 同构（`sseErrorFrame`、`parseQoderSSEChunk`、512B 盲读），需一并修复；`traework` / `zcode` 的 `sseErrorFrame` 无顶层 `code` 判定，但上游协议不同，需单独评估是否同形（不在本轮结论内）。
6. **验证方式**：新增单测覆盖"HTTP 200 + 顶层 code 排队帧"→ 断言立即返回错误且 < 500ms（用 `hangingReader` 模拟 Keep-Alive）；必失败哨兵反证；生产用 §2.1 的 112KB prompt 直测，修复前 60s 挂死 / 修复后应立即报错（或换号成功）。

## 6. 未覆盖与后续风险

- **未覆盖**：`upstream served model "auto" for requested model "Qwen3.8-Flash"`（68 条）——上游把 `Qwen3.8-Flash` 静默路由到 `auto`，属模型键契约问题（`qfmodel` 短请求实测可正常返回正文，故非本次挂死主因），需另立评估。
- **未覆盖**：排队阈值精确边界（本组实测 67KB 通过、112KB 触发；未逐点二分），以及是否与账号积分/时段配额相关。
- **已澄清（本轮补充实测）：排队是「请求级 + 时段性」，不是账号级。** 依据 feed 全量 259 条 qoder-ai qwen 记录：
  - **同账号 ok/bad 混合**：`01a003c5` 25 成功 / 39 失败、`01a125f7` 18 / 21、`01a126db` 34 / 19、`01a126dc` 15 / 11、`01a1241b` 26 / 36 —— 同一账号既能成功也能挂死，排除"账号级坏号"。
  - **成功请求的 input_tokens 高达 289,424**（`01a125f7`，latency 88.9s），远大于失败样本的 ~33K token，说明**上下文长度不是唯一判据**，大请求同样能成功。
  - **失败高度时段聚集**：97 条 60s 挂死集中在 `2026-10-11T15:36 → 16:13Z`（北京 23:36 → 00:13）两个账号（`01a126dc` / `01a126db`）交替出现；按小时聚合显示各时段 ok/bad 比例在 1:1 到 7:1 之间波动。
  - 同一 13K token 的 new-api 渠道测试在 22:18 挂死 124s、在 22:27/22:30/23:00 分别 1.4s/1.5s/2.4s 成功——**同一请求不同时刻结果不同**。
  **推论**：上游排队由**时段容量/队列状态**驱动，修复后**换号不一定救回**（同一时刻多个账号可能同时被排队）。因此修复的首要价值是**快速失败**（60s → <1s 报错），把是否重试/换号留给上层；若要真正提升成功率，需要另做"排队帧出现时的跨 provider 换道或退避重试"策略。
- **未覆盖**：另有 18 条 `latency<3s / status_code=0 / ttft=0` 的快速失败（非 60s 挂死形态），与排队帧不是同一根因，需单独取证。
- **未覆盖**：`retryAfterSeconds:30` 的排队语义下，上游是否期望客户端**等待后重试**而非换号；这影响修复后应"立即报错"还是"短退避重试"。
- **风险**：修复涉及 `stream.go` 与 `active_ping.go` 的公共解析/探活路径，属高影响面改动，须走完整回归（cgo-shim build/vet/test + 6-review + 生产热重载验收）。
- **同名认领治理**：`qwen-3.8-flash` 同时被 qoderwork-provider 与 traework-provider 认领（另见 `project-multi-provider-model-collisions` 记忆），本轮未做任何生产路由变更。

## 7. 结论

new-api 调不通 `qwen-3.8-flash` / `qwen-3.8` 不是模型名解析错误、不是 new-api 配置错误、也不是链路缓冲问题，而是：**大上下文请求被阿里 Qoder 上游投入排队，在 HTTP 200 下返回顶层 `code:"403"`（`10605 / isQueued:true`）排队帧；qoder-ai-provider 的 SSE 解析器与错误帧提取器都不识别该形态，将其丢弃后死等 Keep-Alive 连接约 60 秒，客户端零字节直至超时取消（new-api 记 `client_gone`）**。CPA 面板测试因 prompt 极小（不触发排队）且只做首字节盲判而显示成功，形成"测试通过、真实不可用"的假象。修复入口单一：让解析器与错误帧提取器识别顶层 `code` 错误帧并立即收尾。
