# 生产 Token 用量记录在宿主配置热重载窗口被永久丢弃 + 退役实例导入协程泄漏 根因诊断与修复

- 发生时间：2026-10-11 全日（实测窗口 22:00–23:30，北京时间）
- 影响版本：`workbuddy-token-usage` ≤ 0.2.6（源码目录 `token-usage-tracker`）
- 修复版本：`workbuddy-token-usage` 0.2.7
- 发现途径：0.2.6 发布后的生产验收复核（非用户报障）
- 关联：`doc/4-bugs/2026-10-11_212700_deepseek多服务商同名认领导致推理零首字节断开根因诊断.md`（同一次复核中并行发现）

## 1. 现象

生产 CPA 容器日志两类消息持续出现，且随宿主配置重载成批爆发：

```
[token-usage-tracker] feed: skipping unparsable line: store is closed
[token-usage-tracker] usage.handle: record failed (non-fatal): provider=... err=store is closed
```

读接口同窗口会返回 `HTTP 500 {"error":"store is closed"}`（实测 23:22:43 `/stats/groups` 与 `/requests?days=7` 双双 500，23:23 的 12 次采样又全部 200，属间歇而非永久损坏；`storage disabled` 计数为 0，证明句柄未永久置空）。

## 2. 复现与量化（生产真实数据）

按分钟聚合，驱动因子与损失严格同相：

| 时间 | 宿主 config reload 次数 | 插件 reconfigure 次数 | 记录成功 | 记录失败 |
|---|---|---|---|---|
| 15:00–15:02 | 0 | 0 | 20/26/16 | **0/0/0** |
| 15:03 | 2 | 1 | 7 | 1 |
| 15:04 | 2 | 1 | 4 | **13** |
| 15:06–15:09 | 0 | 0 | 15/15/18/17 | **0/0/0/0** |
| 15:10 | 2 | 1 | 7 | **7** |
| 15:15 | 2 | 0 | 4 | **8** |
| 15:16 | 1 | 2 | 6 | **8** |
| 15:22 | 2 | 1 | 4 | **14** |

结论：在 90 分钟窗口内，**`cfg_reload=0 且 reconfig=0` 的分钟 fail 恒为 0；每次 reload 稳定带走 7–14 条记录**。

### 2.1 重要更正：日志里有两类失败，只有一类是真丢失（2026-10-11 23:49 实测）

随后取更近窗口时相关关系**破裂**：最近 15 分钟 `configured: feed_enabled`、`config file changed, reloading`、`plugin hot reloaded` 全部为 **0 次**，却仍有 **248 条** `feed: skipping unparsable line`。决定性反证是消费位点：

```
cat token-usage-feed.ndjson.offset  -> 94438247
stat -c %s token-usage-feed.ndjson  -> 94438247     # 逐字节相等：全部已消费，无积压、无跳过
store /requests?days=1 total        = 11114
new-api 24h record consume log      = 5046           # 存储侧多于宿主侧，未见缺失
```

因此失败必须拆成两个来源：

| 来源 | 触发 | 是否丢数据 | 量级 |
|---|---|---|---|
| A. 换句柄窗口 | reconfigure（由配置重写引发） | **是**，窗口内在途记录永久跳过 | 每次 reload 7–14 条 |
| B. 退役实例泄漏 | 无（持续空转） | **否**，同一批数据被活跃实例正常入库 | 248 条/15m 纯日志噪声 |

B 的机理：`feedImporterLoop` 由 `importerOnce.Do` 在每个 .so 实例内各自启动一份，宿主热重载只关闭旧实例的 store（`closeCommand` 后 actor goroutine return），**从不通知旧实例的导入循环退出**。旧实例仍按自己的内存偏移 tail 同一个 feed 文件，对已关闭句柄写入 → 持续刷 `store is closed` 警告。

据此撤回本文与测试文档早前给出的"约 22% / 最高 54% 持续丢失"结论：那是把 A、B 两类的分母混在一起算出的**高估**。按 A 类单独计量的真实丢失约为"每次配置重载 7–14 条"，24h 内宿主侧热重载 20 次、另有多次配置重写，属个位数百分比量级，而非半数。

⚠️ 上述"决定性反证"里 `offset == size` 一条**只能证明导入器没有积压，不能证明没有跳过**——真丢数据时偏移同样会追平文件长度。B 类不丢数据的判断因此改由以下两条支撑：(1) 失败发生在 0 次 reconfigure 的窗口，活跃实例句柄未关闭，只能是已关闭句柄的调用方（退役实例）；(2) 活跃实例持续输出 `usage.handle: recorded` 且 store 入库量不低于宿主侧消费量。由此引出 B 类的真正残余风险：**`.offset` 文件是跨实例共享的**，退役实例（跑的是旧代码，失败仍会推进偏移）会把它自己内存中的位置写入该文件；实例重启或热重载后 `loadFeedOffset` 会读到这个被外部推进过的值，此时才可能真的跳过未消费数据。该风险已列入第 6 节，与 feed 轮转判据一起作为后续项。

## 3. 根因（三层，自下而上）

### 3.1 触发层：无关的宿主配置重写

写入源已定位到具体请求：

```
2026-10-11T15:15:15.932Z  PUT /v8/management/config/plugins/configs/gemini-provider/enabled
2026-10-11T15:15:15.933Z  config_reload.go:72 config file changed, reloading: /CLIProxyAPI/mysqlstore/...
```

差 1ms。宿主每次配置重载都会向**所有**插件推送 reconfigure，而重载内容对本插件毫无变化（差分日志为 `payload.*: updated (0 -> 0 rules)` 这类空变更）。生产里每 5–7 分钟就有一次（并行会话的插件安装/启用、账号刷新等都会重写配置）。

### 3.2 放大层：reconfigure 无条件重开 store

`token-usage-tracker/feed_ingest.go` 的 `reopenStore` 原先不比较配置实质，每次推送都 `usagestats.Open` 新句柄、换入并 `old.Close()`。而 `usage_stats/persistence.go` 的 store actor 在 `closeCommand` 里 `db.Close()` 后 **goroutine 直接 return，不会重开**，因此：

- 已在读锁下捕获旧句柄的 `feedImporterLoop` / `handleUsage`，在换句柄后对其发送命令 → `ErrStoreClosed`。
- `ensureStoreOpen()` 只在 `usageStore == nil` 时自愈，对"句柄非空但已关闭"这种在途状态无效。

### 3.3 定性层：偏移先于写入推进，把瞬时窗口变成永久丢数据

`feed_ingest.go` 的 `ingestFeedChunk` 原实现：

```go
consumed += int64(len(line)) + 1     // 先推进
if err := store.RecordFeedNDJSON(line); err != nil {
    trackerWarnf("feed: skipping unparsable line: %v", err)
    continue                          // 后失败，且已消费
}
```

`syncUsageFeed` 据此把 `offset + consumed` 持久化到 `<feed>.offset`，下一轮 poll 不会再回到这些行 → **不是重试队列，是永久丢失**。RPC 通道 `handleUsage` 则按宿主约束必须 ack（返回 error 会触发 `fusePlugin` 永久禁用 UsagePlugin），因此也无法靠调用方重试挽回。

### 3.4 泄漏层：退役实例的 feedImporterLoop 永不停止（独立缺陷，本次未修）

`configure()` 用 `importerOnce.Do(func() { go feedImporterLoop() })` 启动导入循环，`importerOnce` 是**每个 .so 实例各自一份**的包级变量。宿主热重载只会向旧实例下发 `closeCommand`（其 actor goroutine 关闭 db 后 return），**没有任何机制通知旧实例的导入循环退出**。旧实例因此继续按自己的内存偏移 tail 同一个 feed 文件，对已关闭句柄写入并刷警告。

代价不是丢数据（活跃实例已把这些行正常入库），而是：每个退役实例一份常驻 goroutine + 对一个 90MB 级 feed 的周期性重复读取与解析 + 持续污染日志（实测 248 条/15 分钟）。24h 内该插件被热重载多次，泄漏可累积。

彻底修法需要给导入循环一个可取消的 `context`/done 通道，在 `Store.Close()` 或收到 `closeCommand` 时通知其退出；本次 0.2.7 未含，已单列任务。

## 4. 修复（0.2.7）

主修：**消除窗口本身**；辅修：**万一仍有窗口，不得推进偏移**。

1. `usage_stats/persistence.go` 新增可判别哨兵 `ErrStoreClosed`（文案与原 `errors.New("store is closed")` 完全一致，零外部行为变化），替换 `send()`、restore 分支与 `usage_stats/cost.go` 三处产生点。
2. `feed_ingest.go` `reopenStore`：计算存储配置指纹（`DBPath|RetentionDays|FlushInterval|FlushMaxRecords|DerivedSession*`），**句柄已打开且指纹未变时直接复用**，不再换句柄；关闭 feed 或 Open 失败时把指纹置空，保证后续仍能自愈重开。
3. `feed_ingest.go` `ingestFeedChunk`：写入失败且为 `ErrStoreClosed` 时 **break 且不把该行计入 consumed**，偏移停在未写入行之前，下一轮 poll 重新读取；解析错误、超长行仍照常前移（它们是真不可恢复）。空行/超长行的 `consumed` 记账同步改为按分支显式累加，语义与原实现一致。

### 已评估并暂缓的方向

- **`handleUsage` 内部重试一次**（换句柄后对新 handle 再发一次）：主修 2 已经消除了绝大多数窗口，剩下只在"真实配置变更"时才会命中，此时 ack `recorded=false` 丢 1 条的成本远低于在 UsagePlugin 入口新增重试分支带来的时序与 fuse 风险。若后续观测到真实变更窗口仍有可观测量再补。
- **抑制宿主的空配置重写**（找出 5–7 分钟一次的写入方并去掉）：属并行会话的插件安装/启用与账号刷新动作，非本插件可控，且修复后已无损失。

## 5. 验证

见 `doc/5-tests/2026-10-11_233300_Token用量热重载窗口丢记录修复回归.md`。要点：`cgo-shim-build.py token-usage-tracker` build/vet/test 全绿；新增 3 条用例真实执行通过；两处**语义变异**分别还原修复后用例必失败，其中偏移变异的实测数字为 `consumed = 1272, want 0`，即一次重载会跳过 1,272 字节（3 条记录）——与生产每次 reload 掉 7–14 条的量级吻合。

## 6. 现状与残余风险

- 修复只影响本插件的数据完整性，不改任何对外接口结构，前端无感。
- 历史数据不可回补：0.2.7 之前已被跳过的记录不会重新出现，看板与成本统计在 2026-10-11 及更早区间存在系统性偏低，做趋势对比时需知情。
- 上线后需按第 2 节同一口径复测（`cfg_reload>0` 的分钟是否仍出现 fail），预期为 0。
- **相邻既有隐患（本次未修，非本次改动引入）**：feed 的偏移只按 `offset > size` 判定截断（`loadFeedOffset`），而生产侧 `workbuddy/usage_feed.go:225-230` 在超过 128MB 时 `os.Truncate(path, 0)`。若截断发生时消费侧偏移恰好小于新文件长度（需要生产方在下一次 poll 前重新累积到超过旧偏移的字节数），会从新文件的中段开始读，静默跳过一段记录且无法察觉。彻底做法是用"文件身份 + 首行锚点"（如 inode/首行哈希）代替裸偏移判等来检测轮转。触发条件苛刻，本次按最小改动原则只登记不处理。
- **B 类泄漏的真正残余风险（已在 0.2.8 关闭）**：`<feed>.offset` 是**跨实例共享**文件，而退役实例跑的是旧代码（写入失败仍推进偏移并 `saveFeedOffset` 落盘）。只要退役实例的内存位置领先于活跃实例，它就会把共享偏移写到更大的值；此后活跃实例重启或再次热重载时 `loadFeedOffset` 读到被外部推进的偏移，就会**真的跳过中间那段未消费数据**。0.2.8 让退役实例在连续 3 轮关闭后自行退出（`feedImporterLoop` + `importerOrphanCount`），退出后不再读 feed 也不再写偏移，该通道随之关闭。
- ⚠️ **上线边界**：0.2.8 只能让"今后被退役的实例"退出。当天已由 0.2.4–0.2.7 退役产生的泄漏协程跑的是没有退出逻辑的旧代码，宿主热重载无法回收它们，**要彻底清零需要一次容器重启**；按仓库「非必要不重启生产 cpa 容器」红线，该重启需用户明确确认，本次不执行。
- 本次改动带来的边界已核对：偏移停在失败行时 `syncUsageFeed` 因 `newOffset == offset` 不写 `.offset` 文件，下一轮重新读取当前 `usageStore` 句柄，因此不会形成永久卡死；真实配置变更（指纹不同）仍会正常换句柄。
