- 被测对象：`token-usage-tracker/feed_ingest.go`、`token-usage-tracker/usage_stats/persistence.go`、`token-usage-tracker/feed_store_window_test.go`
- 来源对象：`doc/4-bugs/2026-10-11_233200_Token用量记录在宿主配置热重载窗口被永久丢弃根因诊断.md` 第 3.4 节（B 类）与任务 #12
- 执行时间：2026-10-12 00:13–00:18（北京时间）
- 环境：Windows + Git Bash，无 C 工具链，`python scripts/cgo-shim-build.py token-usage-tracker`

## 1. 修复内容

宿主热重载不会通知被退役实例的任何后台协程，而插件的 `cliproxyPluginShutdown` 必须是 no-op（拆除期触碰 Go 运行时有 cgo SIGSEGV 风险，与 workbuddy/qoderwork 同一约束），因此**不能从 shutdown 侧收尾**。改为让实例自己判定并退出：

1. `usage_stats/persistence.go` 新增 `Store.Closed()`（在 `stateMu.RLock` 下读 `closed`），使调用方能判别"句柄非空但已关闭"。
2. `feed_ingest.go` 新增 `currentStoreClosed()` 与纯函数 `importerOrphanCount(closed, previous)`：**连续** `feedImporterOrphanPolls = 3` 轮关闭才判定本实例已退役。
3. `feedImporterLoop` 改为按该判定退出；任一健康轮次把计数清零，因此正常的换句柄不会误杀活跃实例。

## 3. 执行证据

- `cgo-shim-build.py token-usage-tracker`：build / vet / test 全绿。

- gofmt：新增测试文件 clean；`feed_ingest.go` / `persistence.go` 的 gofmt 差异全部落在 `trackerConfig`、`usagestats.Config` 字面量、`Store` 结构体字段对齐区（并行会话新增 `DerivedSession*` 字段所致），**本次新增的行不在任何差异中**，按手术式改动原则不顺手重排。

## 4. 变异反证（覆盖真实）

在临时 shim 副本上还原生产逻辑（不改仓库文件）：

| 变异 | 结果 |
|---|---|
| 去掉健康轮次重置（`if !closed { return 0, false }` 改为永不重置） | `--- FAIL: TestImporterOrphanCountRequiresConsecutiveClosedPolls` |
| 阈值改为 `1 << 20` | `--- FAIL: TestImporterOrphanCount…`、`--- FAIL: TestFeedImporterLoopExitsWhenStoreClosed: retired instance importer loop did not exit`、`--- FAIL: TestFeedImporterLoopSurvivesHandleSwapAndResumes` |

第一轮实现时曾出现"**去掉重置仍全绿**"的情况，说明时序型用例覆盖不到该语义（`2 < 3` 时后续仍能退出）。因此把判定抽成纯函数并补 T1 表驱动用例，之后该变异可被稳定捕获。

## 5. 上线后的可观测边界（重要，实测结果见 §6.1）

本修复只对**今后被退役的实例**生效。今天已泄漏的导入协程来自 0.2.4–0.2.7 的退役实例，它们跑的是没有退出逻辑的旧代码，**宿主热重载无法回收它们**；因此 0.2.8 上线后 `feed: skipping unparsable line: store is closed` 的噪声不会立即归零，要彻底清零需要一次容器重启。按仓库「非必要不重启生产容器」红线，该重启需用户明确确认，不在本次操作范围内。

判读要点：0.2.8 之后新增的热重载不应再产生新的持续噪声源；若某次发布后噪声台阶式上升且长期不降，说明泄漏回归，可用下面命令看趋势：

```bash
docker logs cli-proxy-api --since 15m 2>&1 | grep -c "feed: skipping unparsable line"
docker logs cli-proxy-api --since 15m 2>&1 | grep -c "importer stopping after"
```

### 6.1 退出日志的观测时点（诚实边界）

上线后 5 分钟内 `importer stopping after` 计数为 **0**，这是**预期结果**而非失败：本次被退役的是 0.2.7 实例，它跑的是没有退出逻辑的旧代码，新逻辑只存在于 0.2.8 起的实例里。因此该日志**最早只能在下一次升级退役 0.2.8 实例时出现**（判据：安装 0.2.9+ 后 3 个 poll 间隔内出现 `feed: importer stopping after 3 closed-store polls (instance retired)`）。
